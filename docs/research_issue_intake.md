# 承認済みIssueを読む受付（実験は起動しない）

## 何ができるか

GitHubの公開Issueから、タイトルが `[実行承認済み]` で始まるものを取得し、ローカルのSQLite台帳に記録する。通常の研究Issueや設計Issue #56、PRは対象外。同じIssueを何度読んでも別の依頼として増やさない。

これは #56 の新しい流れの**受付部分だけ**。Codex・CPU実験・GPU実験は起動せず、Issue投稿・ラベル変更・PR作成・マージ・通知も行わない。受け取った指示をシェルで実行する処理はない。

## 使い方

管理側の専用状態ディレクトリで、1回だけ確認する。

```bash
python -m research_harness.issue_intake --once --state /path/to/private-state/intake.sqlite
```

状態ディレクトリは事前に用意する。指定したSQLiteと隣のロックファイルを作る。外部アクセスは固定リポジトリへの未認証のHTTPS GETのみ。トークンや新しい権限は不要。常駐や定期実行の設置はこの変更には含まない。

結果はJSONで出力する。常に `execution_allowed: false`。通信・ページ取得・台帳更新が失敗したら終了コード1で、空キューとは扱わない。取得を完了してから一括記録するため、途中で失敗して部分的な受付結果を確定しない。

## 候補の形式

本文は人向け説明を書き、最後に次のブロックを1つ付ける。以下は書式例であり、承認や実験条件の見本ではない。公開してよい内容のみを書く。

````markdown
目的や条件の説明

```c3-execution-request
{
  "schema_version": 1,
  "plan_version": 1,
  "issuer": "issuer-reference",
  "approval_ref": "approval-reference",
  "expires_at": "2030-01-01T00:00:00Z",
  "cancelled": false,
  "plan": {"purpose": "書式例。実行許可ではない"}
}
```
````

`plan` は現段階では空でないJSONオブジェクトとして保管対象を識別するだけ。実験条件の充足性や実行コマンドの妥当性を検証したとは扱わない。日付や版は本人が承認した値を登録し、この例の値を自動補完しない。

## 承認を偽造させない

接頭辞・Issue作者・本文の `issuer` / `approval_ref` はすべて**自己申告**。本人の承認を証明しない。同じGitHubアカウントから作られたIssueでも、本物とみなさない。

形式が正しく期限内でも `PENDING_TRUSTED_APPROVAL`（信頼できる承認経路が未接続なので保留）になる。実行可能状態や実験の取得枠は作らず、既存の試験用実行台帳にも登録しない。承認を検証する本番経路が完成するまで、設定値でこの制約を解除する機能は提供しない。

## 変更・取消・二重受付への対応

- Issue番号と固定リポジトリで受付を一意にする。SQLiteトランザクションと既存SingleInstanceロックを使う。
- タイトル・本文・作者ID・Issue番号のSHA256を記録する。本文内の版・承認参照・条件もこれに含まれる。
- 変更を見つけたら `CHANGED_REQUIRES_REAPPROVAL`。元の内容へ戻しても自動復帰しない。現在の取消・期限切れ等は `observed_status` に別途残す。
- 接頭辞削除・closeを見落とさないよう、既に記録したIssueを毎回個別取得する。closeを完了・停止証明とは解釈しない。
- 取消の自己申告と期限切れは停止側へ分類する。本物の取消の受信保証はまだない。
- 再起動しても同じDBから読み直す。データの変更や状態変更のない再取得は `duplicate: true`。
- 既存台帳に200件を超える対象がある場合は手動整理を要求し、勝手に履歴を削除しない。一覧は100件×最大20ページ、各応答2MiB、ネットワーク待ち20秒、走査時間120秒の検査で制限する。時間検査はリクエスト間で行うため、OSによる厳密な時間上限ではない。

同一UIDで台帳を書き換えられる作業側との隔離は、このSQLiteやロックだけでは成立しない。本番の制御側状態領域・承認元との権限分離が別途必要。

共有GPUの実行可否は将来の固定管理プログラムが確認する。利用中・割当不明なら待機し、他者のジョブを停止しない。停止権限は所有を確認した自runだけに限定する。nvidia-smiの空き表示だけで利用許可や予約確保を証明したとは扱わない。この受付はGPU管理を行わない。

## 今回の試験と残りの作業

2026-10-17の確認結果：ハーネス試験142件が通常Pythonと `python -O` の両方で成功。公開APIから取得した #56 は `INELIGIBLE`。実際の全open Issue走査は成功し、接頭辞を持つ候補は0件だった。この結果は取得時点の状態であり、承認済みIssueの本物の往復試験ではない。

自動試験は通常Issue・PR・接頭辞だけ・偽の承認参照・取消・期限切れ・改変と復元・再起動・同時受付・通信断・ページ送りを扱う。通常のPythonと `python -O` で確認する。実行機能がないので、これをGPU安全性や本物の承認往復の実証とは呼ばない。

次は本人の承認と登録内容を改変不能に結び付ける経路を決め、その検証器へ接続する。その後に実行側の隔離・上限・停止確認を行い、別途承認した小さなCPU処理へ進む。マージ承認は実行承認とは別。
