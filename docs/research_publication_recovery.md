# 保存済み Issue #77 の公開だけを再開する

## 目的と範囲

#77 は計算結果の保存・再起動確認まで完了した後、実行元コミットと公開先mainの基準を混同したため、公開前にBASE_CHANGEDで停止しました。この処理は、その保存済み候補を新しく承認したmain基準へ届けます。モデル・計算・GPUは起動しません。

元の実行元コミット、候補JSON、成果物hash、承認されたIssue本文hash、claim、再起動記録、元のBLOCKED公開履歴は書き換えません。新しい公開計画と公開履歴を別に記録します。候補の内容は引き続き未検証の申告で、科学的な研究結果ではありません。

## 実施前に必要な承認

専用の旧サービスだけを停止し、その再起動ポリシーをnoに変更します。その後、既存管理用保存領域とGitHub認証を使う、一時的な公開専用コンテナを新規に用意します。この環境への既存認証の利用と設定変更には実施時の明示承認が必要です。秘密をメッセージやログへ出しません。

公開専用イメージはPythonとghだけで、Codex実行ファイル・モデル起動入口・実験workerを含みません。UID10001、capabilityなし、root filesystem読取専用、1 CPU/1 GiB/64 PID、bridge通信、restart=noです。Dockerソケットやホストディレクトリは渡しません。

## 同じ単発コンテナで2段階

1. 旧サービスが停止し再起動しないこと、元の保存領域の利用者が旧サービスと今回の公開コンテナだけであることをホスト側で確認します。
2. Docker inspect/volume inspectの実測値を、管理領域のroot所有0644の準備記録に保存します。管理領域自体はUID10001所有0700です。記録には短い有効期限と明示的なmode=prepareを指定します。
3. 固定の--once入口を起動します。prepareでは元台帳を読取り専用で開き、元結果の同一性、再起動確認、元公開がBASE_CHANGEDで停止し保存済みcontent/PRがなく、現在も対応するブランチ/PRが存在しないこと、main基準を確認します。公開API書込みも新しい公開履歴作成もしません。新しい承認コメントのテンプレートだけを返します。
4. ユーザーがこの新しい公開計画を承認した場合のみ、本人の未編集GitHub承認コメントを登録します。元/新公開計画digest、元成果物hash、Issue本文hash、main基準、復旧コード・イメージ、期限を束縛します。
5. コンテナ停止中に同じ準備記録を新しい実測値で更新し、mode=publishを明示します。同じコンテナを--onceで再起動します。独立したGitHub承認を再確認してから既存publisherを呼びます。modeだけでは承認になりません。

元のサービスを再起動してはいけません。元台帳は意図的にRESULT_READY/BLOCKEDのままです。新しい公開履歴にPRのURLと状態が記録されます。書込み結果が不明な場合は同じ永続履歴から読み取り照合し、履歴を消してやり直しません。mainの変更や承認失効などで安全に照合できない場合は停止し、個別の読み取り確認が必要です。

## 準備記録の所有者を保つ配置方法（Docker 28.3.2）

停止中の公開コンテナへ準備記録をコピーするとき、`docker cp -a` は使いません。この版の実装は `CopyUIDGID=true` の場合、tarのUID/GIDではなくコンテナの `Config.User` を `ChownOpts` に設定します。そのため、このUID10001のコンテナではroot所有を指定したtarでも10001所有になります。

実測値で検証したJSONを、`publication-recovery-77.json` という通常ファイル1件だけのUSTARにします。UID/GIDは0、modeは0644とし、親ディレクトリ・リンク・PAX上書き・絶対パス・`..` を含めません。`docker cp - FULL_ID:/control/ < MANIFEST_TAR` として、`-a` なしでstdinから渡します。既存の準備記録だけを上書きし、親の10001:10001/0700や元台帳を変更しません。

配置後は `docker cp FULL_ID:/control/publication-recovery-77.json -` のtarを読み戻し、通常ファイル、UID/GID 0、0644、JSON完全一致を検証してから起動します。ホストへ通常展開したファイルの所有者で判定してはいけません。tarだけで実ファイルのリンク数は証明できないため、固定入口のリンク数検査も維持します。不一致なら起動せず停止します。観測記録が古い場合は実際のinspectを再取得し、有効期限と検証も更新します。

根拠：Docker 28.3.2の[コピー入口](https://github.com/moby/moby/blob/v28.3.2/daemon/archive_unix.go)、[Config.Userによる上書き](https://github.com/moby/moby/blob/v28.3.2/daemon/archive_tarcopyoptions_unix.go)、[通常のtar設定](https://github.com/moby/moby/blob/v28.3.2/daemon/archive_tarcopyoptions.go)。この手順訂正はコード・イメージ・実行元SHAの変更を必要としません。

## 検証の限界

ローカルでは隔離されたダミーtransportで、元台帳が変わらないこと、承認・基準変更・不明な書込み・重複に対する動作を検証します。開発環境にはDockerがないため、この新しいイメージの実機ビルドと公開は別途確認が必要です。承認のない追加試行や実験の再実行には使いません。

## 公開通信の診断

公開履歴の既存reason欄に、HTTP_401/403/422/429、HTTP_500〜HTTP_599、HTTP_OTHER、TIMEOUT、MALFORMED_RESPONSE等の固定分類を保存します。応答本文、ヘッダ全文、stderr、認証値は記録しません。HTTP応答を観測したことは記録できますが、書込み副作用の有無をそれだけで保証しません。UNKNOWN状態は従来どおり読取り照合だけを行い、PR不在でも自動再POSTしません。

未解決の最初の診断を保持し、次の確認済みphaseへ進んだときに解除します。旧reason=nullの履歴も読めます。これは修正版で新しく観測した情報だけであり、#77で過去に失われたPOST応答のHTTP statusを復元するものではありません。後続GETの診断を過去POSTの原因と解釈してはいけません。
