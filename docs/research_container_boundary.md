# 専用コンテナ内で管理担当と実行担当を分ける検証

## 何を確かめるか

管理用の認証や台帳を、実行担当のCodexから読んだり変更したりできない構成を作るための、小さな事前試験です。今回は実際の認証情報やCodexを使わず、ダミーのファイルと短時間のPythonプロセスだけを使います。成功しても実験の実行許可にはなりません。

## 構成

すべてユーザー専用の1コンテナ内です。起動処理だけがrootで、必要な権限はSETUID/SETGIDのみ。管理プロセスはUID 10001、実行プロセスはUID 10002に切り替え、両方の実効・許可・ambient capabilityがゼロ、補助グループなし、no-new-privileges有効であることを確認します。管理領域/controlと実行領域/workは各UID専用の一時領域です。

Dockerソケット、ホストのホーム、研究データ、認証情報、GPUは渡しません。ネットワークなし、ルートファイルシステムは読み取り専用、CPU 0.5・RAM 128MiB・PID数16・各一時領域1MiBの上限を指定します。専用のseccomp/AppArmor緩和や入れ子のsandboxは使いません。イメージ作成時のみ公式Pythonイメージの取得が必要です。

## 試験項目

- 実行UIDが管理用ダミー認証・台帳を読み書きできない
- 管理プロセスの/proc/environ、mem、開いたファイル記述子を読めない
- 管理プロセスへsignal 0の権限確認が拒否される（実際の停止シグナルは送らない）
- 実行UIDがrootになれない
- 実行側へ認証環境変数を引き継がず、Dockerソケットも存在しない
- 実行側は自分の出力領域には書ける

対象が存在しないエラーは隔離成功と数えません。すべて成功した場合だけ終了コード0を返します。出力のexecution_allowedは常にfalseです。管理プロセスは15秒、実行プロセスは10秒、起動処理は25秒の時間制限を持ちます。既存プロセスや他の利用者のジョブを探索・停止する機能はありません。

## 実施前に必要なこと

このPRの作成・マージは、研究室マシンへの導入や新しいセキュリティ設定の承認とは別です。ユーザーが実施を承認した後、ホストの操作者が次の専用診断だけを実行します。既存コンテナは変更しません。Composeプロジェクト名が既存のものと重ならないことを確認してください。

```sh
docker compose -p c3-boundary-diagnostic -f tools/container_boundary/compose.yaml build
docker compose -p c3-boundary-diagnostic -f tools/container_boundary/compose.yaml run --rm boundary-check
```

これは無認証の有限診断です。gh login、トークン作成・保存、常駐サービス設定はしません。診断用イメージは残ります。

## 検証状況と残る条件

開発環境にDockerがないため、実コンテナでのビルド・起動・UID分離は未検証です。Python単体テストは判定ロジックと構成の退行を確認するもので、実際の隔離成功を代替しません。

この試験はファイル・プロセスの基本的なUID境界を確かめるものです。同じコンテナのカーネル境界、通信、共有IPC、資源独占、実際のCodexの動作、モデル課金制限、公開処理の正当性まで保証しません。本番では管理用認証を実行側から見せない配置の実機検証と、別途承認された最小CPU試験が必要です。管理認証の導入前に保存先・利用権限・用途を示して承認を受けます。
