# Issue受付からダミー結果保存までの接続試験

## 目的

承認を確認する処理と、コンテナ内で別ユーザーとして動く処理をつなぎます。これは通信・台帳・重複防止を確認する診断です。GitHub上の実Issueや実認証は使わず、合成したIssueと承認コメントを、既存の受付・承認照合コードに渡します。合成コメントは本人の承認の証拠ではありません。

実行する内容は100個の整数の平方和を求める固定ダミーだけです。任意コマンド、モデル、研究実験の実行経路はありません。すべての結果でexecution_allowed=falseを維持します。

## 流れ

1. 管理UID 10001が合成Issueと承認コメントを照合する
2. 管理領域のSQLiteに処理権を先に記録する
3. 起動処理が固定のダミー処理を実行UID 10002へ渡す
4. 管理UIDが結果の全フィールド・計画の識別値・平方和を再計算して照合し、承認状態も再確認する
5. 管理領域の台帳へ結果を保存する
6. 台帳を閉じて再度開き、同じ候補を見ても二重に処理しないことを確認する

通信は起動処理が管理する標準入出力のパイプだけです。実行担当に管理側のファイル記述子や認証環境変数は渡しません。実行担当の出力は未検証データとして扱い、管理側が固定形式と内容を検証します。結果をコマンドとして解釈しません。

## 停止する場合

- Issueの内容・承認の変更、取消、期限切れ：拒否
- 処理権を記録した後の停止・通信失敗：記録を保持し、自動再実行しない
- 結果不一致・処理中の承認取消：完了扱いにしない
- 既に完了済み：結果を維持して重複処理を省略する

同時起動は管理側の固定ロックで止め、台帳の主キーも重複取得を拒否します。実プロセスを検索して停止する機能はなく、固定ダミープロセスのみ短い期限で終了します。

## 実機試験について

#69と同じ専用コンテナのUID切替権限（SETUID/SETGIDのみ）を使います。新しい試験の起動は具体的な承認後に実施してください。マージだけで実行されません。

```sh
docker compose -p c3-intake-flow-diagnostic -f tools/container_boundary/compose.flow.yaml build
docker compose -p c3-intake-flow-diagnostic -f tools/container_boundary/compose.flow.yaml run --rm flow-check
```

プロジェクト名は既存のものと重複しないものにします。ホストマウント・GPU・実認証・ネットワークはありません。Dockerfile専用の.dockerignoreは、必要な診断コードと既存ライブラリだけをビルドへ渡す許可リストです。失敗時に権限を追加したり、既存のコンテナや他者のジョブを止めたりしないでください。

成功時はfirst.phase=COMPLETED、first.dispatched=true、after_reopen.duplicate=true、after_reopen.dispatched=false、result_saved=trueを出力します。execution_allowedはfalseのままです。
