# 本人の承認コメントを確認する（まだ実験は動かさない）

## 目的

#66 の受付に続く、承認記録の確認部分。本人がdotへ承認した後、dotがGitHubへ残す記録を管理プログラムが確認する。新しいアカウントや署名鍵を必須にしない。

信頼するのはGitHub上の `ken2129`（固定ユーザーID `55587773`）本人と、その権限を使うdot。GitHubが返す作者・編集情報を使う。コメント本文に「本人です」と書いてあっても信用しない。

**このPRでも実行は常に禁止。** 承認記録が一致しても、共有マシン上のworker隔離・実行環境・停止手段を確認できていないため、Codexや実験は起動しない。マージ操作も行わない。

## 何をチェックするか

- Issueの接頭辞、形式、版、有効期限、取消、変更履歴の受付結果
- 承認コメントの作者IDとログイン名
- GitHubの編集情報が取得でき、未編集で非表示にもなっていないこと。編集者が本人でも編集済みコメントは受理しない
- 固定リポジトリ、Issue番号、計画版、タイトル・本文・作者を含むhash、有効期限が一致すること
- 承認が `approve-execution` であること。マージ承認とは別
- 同じ依頼に複数の承認があれば曖昧として停止。取消記録があれば停止
- 読み取り前後でIssueが変わっていないこと。初回に固定したコメントID・内容hashが後から変わっていないこと。一度確認した取消や承認失効は台帳に残し、取消コメントが消えても自動復帰しない

承認コメントの編集検査にはGraphQLの `author`、`editor`、`lastEditedAt` を使う。フィールド欠損を「編集なし」と解釈しない。RESTの作成時刻と更新時刻が等しいだけでは判定しない。

[GitHub公式のIssueComment仕様](https://docs.github.com/en/graphql/reference/issues#issuecomment)

## Issueと承認コメントの関係

1. dotが本人に条件・上限を提示し、明示的な実行承認を確認する。
2. 承認された内容のIssueを作る。Issueのrequestブロックは `issuer: "ken2129"`、`approval_ref` はその依頼固有の識別子とする。
3. Issue本文を確定してhashを計算し、同じIssueへ次のJSONコメントを投稿する。
4. 受付と承認確認が一致しても、この段階では実行を許可しない。

以下は書式説明。コードはコメントを投稿しない。実験条件や期限を勝手に補完しない。

```json
{
  "schema": "c3-owner-approval-v1",
  "request_id": "Issueのapproval_refと同じ値",
  "repository": "ken2129/c3_neural_compression",
  "issue": 123,
  "plan_version": 1,
  "content_sha256": "確定したIssueのcontent_hash関数の値",
  "expires_at": "本人が承認したIssueと同じUTC期限",
  "decision": "approve-execution"
}
```

取消は同じ対象の `decision: "cancel-execution"` を新規コメントにする。ただし本機能は1回の確認だけで、稼働中の取消通知・停止の保証は実装しない。編集や削除によって過去の承認を消したときも、次回検証は成功しない。実行用の再承認や再試行の復旧操作は別途設計・確認が必要で、自動で台帳をリセットしない。

## 管理側での確認コマンド

```bash
python -m research_harness.owner_approval --issue 123 --state /path/to/private-state/intake.sqlite
```

管理側に既存の `gh` 読取認証があることが前提。CLIはログインや資格情報の設定を行わない。認証がない・APIが不完全・検証に失敗した場合は終了コード1。成功時も `execution_allowed: false`、理由は `WORKER_ISOLATION_AND_RUNTIME_NOT_VERIFIED`。

GraphQLは固定query・固定リポジトリ・数値Issue番号を使う。Issue内のURLやコマンドは実行しない。承認コメントの全文や認証エラーの詳細はログに出力しない。応答の2MiB検査は受理するサイズの制限で、subprocessの出力メモリ上限ではない。SQLiteは受付と同じロックを使う。

## 本番接続前に必要な一回の準備

- 実行workerからGitHub書込認証、GitHub MCP、SSH agent、管理台帳と管理用設定を切り離す。ホストのホームやDockerソケットを渡さない。管理側・台帳・検証器・投稿側・workerはユーザー専用コンテナ内に収め、コンテナ内でもUIDと権限を分ける。ホスト側の常駐管理プログラムを前提にしない。
- `gh` 認証と台帳は信頼する管理側だけに置く。同一UIDや別tmuxだけでは分離できたと扱わない。
- これらの隔離と共有GPUの利用許可・待機・自runだけの停止を実機確認する。利用中・割当不明なら待機し、他者ジョブは停止しない。
- その後、本人が承認した小さなCPU処理で確認する。

新しいアカウント・鍵が必須という意味ではない。既存ownerの権限を作業側が使えないことが前提。本PRはそのOS境界を設置・証明しない。承認記録の一致は、計画内容の安全性や実験条件の正しさを保証しない。
