# Codexで計画案を作る接続口

## 何が増えたか

Issueを読んだあと、計画担当のCodexへ決まった形式で依頼し、返ってきた計画を検査する部分を追加した。
既存の `draft_plan()` に `CodexPlanner` を渡せる。正常な応答はそのまま計画提出機能へ渡せるが、**公開前の確認は別途必要**。

1. 管理側が対象Issue・参照commit・計画の版を決める。
2. 計画専用の環境、利用料金の制限、停止処理が確認できなければ止まる。
3. 固定したCodex実行ファイルを確認し、読み取り専用の隔離起動を事前検査する。
4. Codexに公開済みIssueの内容を渡し、目的・条件・未決定事項をJSONで受け取る。
5. 形式や対象が違う応答を拒否する。正しい応答も実験の許可にはしない。

**この変更だけでは、自動生成を運用開始できない。**
実行環境に接続する `Runtime` の本番用実装は含まない。設定なしではCodexを起動せず停止する。
外部サービスを呼ぶ実生成の試験も完了していない。テストは代役の実行環境で行った。

## なぜ実行環境を分けるのか

Issueには自由な文章が書ける。その文章から、ファイルの読取りやGitHub投稿を指示されても実行してはいけない。
CLIの `read-only` は書込み制限であり、親の認証情報まで読めないことを保証するものではない。
そのため、公開担当のGitHub・Box認証を持たない専用環境からだけ起動する。
同一ユーザーIDの別フォルダや、コード内の「安全」というフラグは、この境界の代わりにはならない。

`Runtime.verify()` は保護された管理側で実装する。Issue・モデル出力・計画JSONから作った値を渡してはいけない。
`RuntimeEvidence` は管理側が確認した制限の参照番号を運ぶ入れ物で、単体で安全性を証明するものではない。

本番の実行環境に必要なもの：

- 固定したCodexバイナリを、管理側と実行側で同一の変更不能な配備物として保持する。検査から生成完了まで、ファイル置換・別mountへのすり替えを防ぐ。ハッシュの一度の確認だけではこの性質は保証できない。
- 計画用の入力と既存のOpenAI認証だけにアクセスできる隔離。公開担当の認証、親のホーム、研究データ、他の利用者のファイルは見せない。
- MCP、プラグイン、hooks、親の設定、環境変数を引き継がない。モデルのツール権限を広げない。
- 外側で強制する時間・出力量制限。停止時と親の終了時には子孫を含む自分のジョブ全体を停止・回収する。
- サービス側で強制する利用上限。CLIの時間制限だけでは料金の厳密な上限にならない。
- ログに認証情報を残さないこと。生成結果を公開する前の内容確認。

これらの条件をこのPRが実装・検証済みとはしていない。専用環境への導入は次の作業となる。

## 生成アダプタ側の制限

- CodexバイナリのSHA256、モデル名、時間上限は管理側で指定する。Issueからコマンドや環境変数を受け取らない。
- 最大入力120,000バイト、最大応答400,000バイト。生成の時間上限は最大300秒、事前検査は10秒。
- 生成の自動再試行なし。隔離の事前検査に失敗したら、安全設定を弱めて再試行しない。
- `--strict-config` で未知の設定を拒否。対応しないCLIでは停止する。
- Issue内の指示は資料として扱い、固定の依頼文と分離する。これは入力上の対策であり、隔離の代わりではない。
- 構造化出力の指定に加えて、既存の厳密な `PlanDraft` 検査を再実施する。
- 実験、GitHub投稿、承認発行、常駐、マージを行う機能はない。

## 今回の実機確認

2026-10-17、開発環境の既存Codex CLI 0.159.2で、モデルを呼ばずに読み取り専用sandbox内の `/usr/bin/true` を試した。
`app-server socket directory must be a user-owned directory with mode 0700` で停止した。
既存設定に触れない一時HOME/CODEX_HOME/XDG_RUNTIME_DIRでも同じ結果だった。
認証の複製・共有ソケットの変更・sandbox回避は行っていない。

したがって、次の実動作確認は、既存認証を正規に利用でき、通常のsandbox起動が成功する専用環境で行う。
まず公開された架空のIssueだけで生成と形式検査を確認する。実験やGPUは使わない。

## 検証範囲

新しいテストは、固定した起動引数、隔離検査での停止、対象のすり替え、不正JSON、出力量、実行ファイル変更、未設定時の停止を確認する。
実Codexの推論、外部側の隔離・料金制限・プロセス回収、実GitHub投稿の成功を証明するものではない。

CLIの設定はバージョンに依存する。実行に使う版とバイナリを固定し、変更時は再確認する。
参考： [公式CLIリファレンス](https://developers.openai.com/codex/cli/reference/)、[公式設定リファレンス](https://developers.openai.com/codex/config-reference/)。

## 研究室マシンで最初に確認すること

上記のエラーはdot側の開発環境での結果であり、研究室マシンの現在の結果ではない。
研究室への導入前に、操作者が次を個別に確認する。認証の内容や設定ファイルは表示しない。

```sh
codex --version
codex exec --help
codex sandbox --help
```

その版で上記の設定形式が対応していることを確認した後、モデルを呼ばずに隔離起動だけを調べる。

```sh
timeout 10 codex -c 'sandbox_mode="read-only"' sandbox /usr/bin/true
```

これは実験やGPUを起動せず、`true` を読み取り専用の隔離環境で起動する確認。
CLIが通常作る一時ファイル等は生じ得るが、研究リポジトリや共有設定を変更するコマンドではない。
終了コード0なら「この隔離起動が成功」まで確認できる。認証の分離、料金制限、研究ループ全体の準備完了を意味しない。
エラーなら文面と終了コードだけを共有し、危険な起動オプションや権限変更を加えない。
これらをdotが研究室マシン上で実行したとはしていない。
